## Problem

A first build teaches you what the product actually is, usually by getting several things wrong. The tempting move is to patch the first version forever. The more honest one is to build it again with what you learned — but a second build is only worth defending if you can point at what changed and why. Most rewrites cannot; the old version is gone, and the argument for the new one is a story nobody can check.

## Idea

Keep both builds live and let them be compared directly. Aurora Voyage was the first take at an itinerary studio: three files — HTML, CSS, JS — a light studio interface, a Leaflet map on OpenStreetMap, and a scope stretched across managing multiple trips. Voyagr is the same product rebuilt as one self-contained file with a dark editorial identity, deliberately narrowed to single-trip depth, and carrying features the first version never had — a packing list, trip stats, and conflict detection.

This is the [prototype-first](/work/prototype-first) argument made concrete: the fastest way to understand a product is to build it, and the fastest way to understand what to build next is to look honestly at what you already built.

## Mockup

The showcase pairs the two, tells the evolution in a line — three files to one, light to dark, broad to focused, more capable in v2 — and embeds both apps live so the difference is operable rather than described. Both are frontend-only and work offline.

## Prototype

Both versions run in the browser with no backend. Preserving v1 instead of deleting it is the whole point: it turns "the new one is better" from a claim into something you can check by clicking between them. The interesting output is not either app but the diff — the specific decisions the first build earned the right to make in the second.
